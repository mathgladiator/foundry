# Organizing the source

This document describes how the source tree is organized. The host, runtime, and systems are written in C++, and the game-facing API is plain C.

## The tree

| Path | Language | What lives there | Ships in the game? |
|---|---|---|---|
| `src/host/$namespace/` | C++ | The foundry application: one directory per vertical slice | No |
| `src/runtime/$namespace/` | C++ | The engine for dynamic content, including the mega shader | Yes |
| `src/library/` | C headers, C++ implementation | The game-facing C API: `runtime.h` and its fragments | Yes |
| `src/systems/$name_$version/` | C++ | One runtime system version, such as `tree_rig_v1`. Static assets are transforms in the host instead (`design/transforms.md`) | Yes, merged into the runtime |
| `src/channels/` | JSON | Channel schemas: the contracts between runtime systems. The generator turns each into C++ under `src/generated/` | Yes, as generated code |
| `src/common/` | C++ | Small header-only libraries shared by systems, starting with `boundary.h` | Yes |
| `src/tools/$tool/` | C++ with a C header | Tools built against the runtime the way a game is, starting with the stress platform (`design/quality.perf.md`) | No |
| `src/generated/$namespace/` | C++ | Code generated by the host, never edited by hand | Yes, where the runtime uses it |

Outside `src/`:

| Path | What lives there |
|---|---|
| `tools/` | `bootstrap.sh` (prebuilt toolchains), `gen_channels.py` (the channel generator), and `gen_pipelines.py` (the pipeline generator: API fragments, native executors, stress bindings) |
| `tests/` | Native tests, run with `ctest` |
| `cmake/` | Dependencies and the `foundry_add_system` build function |

| `book/` | One document per pipeline, `book/$pipeline.md`: how to use it, how it's built, its flow, performance, and QA (`CLAUDE.md`, "Documentation") |
| `demo/` | The workspace root for developing the foundry: the project's data and its `foundry.json` |

## The workspace

The source tree and a project's data are separate. The foundry runs against a **workspace root** (`--workspace`, default `demo/`), which holds:

| Path | What lives there |
|---|---|
| `foundry.json` | The workspace's configuration: the MCP address, the Meshy keys file, and the Meshy credit budget |
| `pipelines/`, `conformance/` | Pipeline descriptions and conformance shapes |
| `config/` | Config tables: named records of one channel that a pipeline picks from by name, such as `tree_v1_genomes/oak.json` (a `tree_v1_genome` value plus state and notes) beside the table's `table.json` (`design/flow.md`, "Config") |
| `reference/` | Reference photos (public domain or CC0) with provenance sidecars, which config entries link to and the viewport shows in its corner (`design/flow.md`, "Reference") |
| `meshy/` | The Meshy scratch pad (`<name>_concept`, `<name>_mesh`) and the credit ledger |
| `fixed/` | Stamped fixed assets |
| `perf/` | Stress plans, and the committed stress reports that form the performance timeline (`design/quality.perf.md`) |
| `qa/videos/` | QA videos of pipelines and their indexes; regenerated, not committed |

Systems and channels stay in the source tree (`src/systems/`, `src/channels/`), since they're code. `demo/` is the workspace used while developing the foundry itself; a game would have its own.

## `src/host/$namespace`: the foundry application

Each namespace is one directory and one vertical slice of the host, with clear bounds. For example, HTTP and MCP together form one slice.

Slices talk through interfaces, not through each other's internals. The MCP slice shows the pattern: an MCP handler interface separates the server (which speaks the protocol) from execution (the code that does the work). The server parses requests and dispatches them to handlers; handlers never see HTTP or MCP details. This keeps the protocol replaceable and the work testable without a server.

The slices so far:

| Slice | What it does |
|---|---|
| `core` | Configuration, the activity log, background jobs (the status bar), and small utilities (files, JSON, base64, processes) |
| `mcp` | The MCP server (JSON-RPC over HTTP on localhost) and the handler interface every other slice registers tools through |
| `wasm` | Runs system modules in Wasmtime: a fresh sandboxed instance per run, with fuel and memory limits |
| `forge` | The system lifecycle: create, write source, build (WebAssembly and native), run, and compare native output with WebAssembly output |
| `workspace` | The workspace model: items, manifests, approval state, notes, and selection |
| `viewport` | The software renderer for the viewport and screenshots, and image encoding |
| `assets` | The asset-pipeline transforms (`design/transforms.md`): GLB import, sizing and the hull estimator, the progressive mesh, LOD recommendation by image error, vertex-cache optimization (meshoptimizer), the foundry mesh file format, Meshy mesh items, stamping, and fracture (`fracture.h`: Voronoi cuts of LOD1 with capped faces and a baked rigid-body break; `fracture_item.h`: the `fracture:<name>` item beside a fixed asset) |
| `meshy` | The Meshy client, with the credit budget and ledger |
| `app` | The entry point, the Dear ImGui workspace UI, and window capture |
| `perf` | The performance phase: GPU benchmarks of meshes, using the runtime's instanced renderer; running pipelines' stress binaries (`perf_stress`) and QA video exports (`pipeline_video`) as background jobs |
| `pipeline` | Runs pipelines in WebAssembly: parameter bindings, a cache of each stage's output keyed by system build and input, the live instance the workspace shows (its clock and background rebuilds), CPU skinning for the viewport, contact sheets, config tables (`config.h`: generic; no pipeline is known to the host), and the flow analysis and probe (`flow.h`) |

Each slice registers its own MCP tools in a `tools.cpp`.

The host never ships in the game.

## `src/common`: shared headers for systems

Systems are self-contained apart from a few small header-only libraries. The first is `src/common/boundary.h`, which helps pack and unpack data at channel boundaries: reading and writing little-endian values, aligned offsets, and fixed-size arrays in a byte buffer. The generated packers and disk formats use it, and so can systems. It also holds:

- **`FOUNDRY_SYSTEM`**, the macro that declares a system's entry point: the WebAssembly exports in one build, and a native entry point in the other.
- **`foundry::det`**, deterministic math (`sin`, `cos`, `hypot`). C library math can differ in the last bit between glibc (native) and wasi-libc (WebAssembly), which would make native output differ from what was approved. Systems use `foundry::det` instead of `<cmath>` transcendentals, and both builds compile with `-ffp-contract=off`. Anything added to `src/common/` is shared by every system, so it should stay small and change rarely.

## `src/generated/$namespace`: generated code

Everything the host generates lives under `src/generated/`, with one namespace (directory) per kind of generated code, added only when there is good cause:

- `src/generated/channels/`: the C++ structure for each channel schema.
- `src/generated/packer/`: the code that packs each channel into a `byte[]` and unpacks it. It is header-only, so systems use it inside WebAssembly too.
- `src/generated/disk/`: the code that writes each disk format and reads it back.
- `src/generated/json/`: conversion between channels and JSON, used by the host's MCP tools to run systems with JSON input.
- `src/generated/stress/`: each pipeline's stress binding, `stress_$pipeline.c` (`design/quality.perf.md`).

`tools/gen_channels.py` generates all of it from `src/channels/*.json`.

Generated code is committed, so changes to it show up in review, but it is never edited by hand: the build regenerates it and fails if the committed copy differs.

## `src/runtime/$namespace`: the engine

The runtime core and everything that supports the graphics engine: instances, update and sleep, the submit queue, caching, and the mega shader (`design/submit.md`). Everything here is expected to run inside the game, so the runtime must never depend on the host.

So far it holds:

- `src/runtime/core/`: the runtime's world (`world.h`): instances and their timelines, the shared cache of builds, generation on background threads, the update broadcast on a thread pool, sleep, culling, and diagnostics; and the interface a pipeline implements (`pipeline.h`), which generated code fills in.
- `src/runtime/shaders/skinned.hlsl` and `src/runtime/render/skinned_renderer.*`: skinned, instanced drawing, with bones streamed in a storage buffer.
- `src/runtime/shaders/cel.hlsl`: the first cut of the mega shader, compiled to SPIR-V by DXC at build time and embedded in the binary (`build/*/shaders/`). DXC comes from `tools/bootstrap.sh`; `SDL_shadercross` will add Metal and Direct3D 12 later.
- `src/runtime/render/`: the engine's in-memory mesh (`runtime::Mesh`) and the instanced cel renderer on SDL3's GPU API, built as the `foundry_runtime` library.

## `src/library`: the C API

The game-facing C API (`design/api.md`) lives here. It is split into fragments so it can grow without becoming one unmanageable file:

- `src/library/$fragment.h` declares one area of the API (instances, events, lights, the shader, one pipeline).
- `src/library/$fragment.cpp` implements it, on top of the runtime.
- `src/library/runtime.h` is the concatenation of the fragment headers, in a fixed order.

`runtime.h` is produced mechanically, never edited by hand, so it stays predictable and stable. The build regenerates it and fails if the committed copy differs. Fragments for pipelines are themselves generated from the pipeline JSON files by `tools/gen_pipelines.py`: `$pipeline.h` (enums, the parameter struct, spawn, setters, and event triggers) and `$pipeline.cpp` (the native executor: each system called directly, its config tables compiled in). `foundry.h` is the handwritten first fragment, `internal.h` is the implementation's view of the runtime, and `runtime_diag.h` holds diagnostics for development builds (`design/quality.perf.md`), never part of `runtime.h`. The library builds as `foundry_library`, with every system's static library linked in.

`runtime.h` is the only header a game includes.

## `src/systems/$name_$version`: systems

Each system version is its own directory, written in C++. Systems should stay simple: plain structures and functions, no exceptions or global state. Systems may use the C++ standard library. It makes every WebAssembly module bigger, but that only costs memory on developer machines, and in the native game build the duplicate copies collapse into one. Each one builds two ways:

- as a **WebAssembly module**, which the host loads in development; and
- as a **static library**, which is merged into the native runtime.

### Versions as namespaces

Each system version lives in its own C++ namespace, named after its directory (`chest_lid_v3`), as `design/spine.md` describes. The build checks each system's static library and fails if it exports any symbol outside that namespace. This lets several versions of one system link into the same runtime.

### Systems are private

Systems are private details of the runtime. A game never sees a system: the API is about pipelines, their parameters, and macro-level configuration such as quality, camera, and lights. No system escapes the runtime:

- `runtime.h` never includes anything from `src/systems/`, and no system name, version, or channel type appears in the API.
- The build checks this mechanically: the API headers may only reference other `src/library/` headers and SDL3.

### Isolation with git

Work must never leak into previously approved systems. Each system's manifest records whether it is final, and a check compares the changes in git against those manifests: any change to a file inside a final system's directory fails. The check runs as a pre-commit hook and in the build, so a batch of agent changes can be reviewed with confidence that approved systems are untouched.

## Build layout

Each platform and configuration gets its own build directory, `build/$platform-{release,debug}`, defined as CMake presets in `CMakePresets.json`:

```sh
tools/bootstrap.sh                      # once: prebuilt toolchains into .deps/
cmake --preset linux-release            # configure into build/linux-release
cmake --build --preset linux-release    # build everything
```

| Platform | Status |
|---|---|
| `linux-release`, `linux-debug` | Supported now, fully. |
| `win32-release`, `win32-debug` | Planned, lower priority. |

Planning for Windows means avoiding Linux-only assumptions where it's cheap to do so: paths go through `std::filesystem`, and process spawning, the bootstrap script, and the locally extracted X11 headers are the known Linux-specific pieces. wasi-sdk, Wasmtime, SDL3, and Dear ImGui all have Windows builds, and SDL3's GPU API uses Direct3D 12 or Vulkan there.

Inside each build directory, the host knows where to find system outputs (and new systems are picked up automatically, since CMake re-globs `src/systems/*/system.json` on every build):

| Path | What it is |
|---|---|
| `wasm/$system.wasm` | A system's WebAssembly module, which the host loads |
| `native/run_$system` | A system's native runner, used to check that native output matches WebAssembly output |
| `stress/stress_$pipeline` | A pipeline's stress binary (`design/quality.perf.md`) |
| `foundry` | The foundry application |

## Dependencies

| From | May depend on |
|---|---|
| `src/systems/` | `src/channels/` and `src/common/` only |
| `src/runtime/` | `src/channels/`, `src/common/`, `src/generated/`, systems through generated registration code, SDL3 |
| `src/library/` | `src/runtime/` |
| `src/host/` | everything above, plus its own third-party libraries |
| `src/tools/` | `src/library/` only (`runtime.h` and the diagnostics header `runtime_diag.h`), plus its own third-party libraries |
| a game | `src/library/runtime.h` only |

Systems are isolated verticals: everything a pipeline needs lives in its systems, its channels, its pipeline file, and its config tables, never in the host or the runtime. The host and the runtime include no channel's generated structure or packer (the host reaches channels only through the generated JSON registry, by name), name no pipeline, system, or channel in code, and treat drawable models and poses by the field convention in `design/flow.md` ("Pipelines"). Pipeline-specific code is generated (`src/library/$pipeline.*`, `src/generated/stress/`), never written into the host.
