# 2026-10-10, session 1

The first day of the foundry, from an empty repository to a working workspace that turns concept art into stamped, benchmarked fixed assets. The proof-of-life milestone's work is delivered and waits for the human's validation; its TODOs and the agent's status moved here from `PLAN.md`.

## The day in brief

1. **Design.** The design documents were cleaned up and expanded through the inline question-and-answer loop: `spine`, `systems`, `playtest`, `flow`, `submit`, `sounds`, `third.party`, `api`, `future`, and `style`, plus `ORG.md`, `CLAUDE.md`, `PLAN.md`, and `README.md`. Key decisions: versions that can be marked final and must be forked, isolated C++ namespaces per version, systems hidden behind a macro-level C API, and a human gate on every step.
2. **The build.** CMake presets (`linux-release`, `linux-debug`) build the host, every system to WebAssembly (`wasi-sdk`) and to native, and the tests. `tools/bootstrap.sh` fetches prebuilt dependencies into `.deps/`, including X11 headers without root.
3. **The workspace.** An SDL3 GPU and Dear ImGui window with the workspace tree, a cel-shaded viewport against the conformance capsule, the hero, and the hex, and an inspector with notes and Approve / Reject. MCP over HTTP on localhost drives all of it, and the agent can see what the human sees.
4. **The gap: transforms.** Building the first pipeline showed that most asset work happens once, in the foundry, and doesn't belong in runtime systems. `design/transforms.md` records the gap; the mesh work moved into host transforms, and the experimental systems and channels were removed.
5. **Two fixed assets.** A garden gnome (`prop_tiny`) and a gargoyle statue (`prop_medium`) went from Meshy concept art to approved, stamped fixed assets with LODs, switch distances, and GPU budgets.

## Decisions

These were settled before starting:

| Decision | Choice |
|---|---|
| UI toolkit | Dear ImGui, on its SDL3 GPU backend |
| Build system | CMake, with two toolchains: the native compiler for the host and static libraries, and `wasi-sdk` (Clang targeting WebAssembly) for systems |
| WebAssembly host runtime | Wasmtime, through its C API |
| MCP transport | HTTP on localhost; Claude Code connects with `claude mcp add --transport http` |
| Meshy budget | 250 credits for this milestone without asking. At current prices that is roughly 6 to 8 static meshes taken from concept image to remeshed 3D, so start with one or two and ask before generating in bulk. |

## Status from the agent

What's built (details in `ORG.md`, `CLAUDE.md`, and `design/transforms.md`):

- **UI:** `build/linux-release/foundry` opens the workspace on `demo/`: the tree, a viewport that draws the selected asset in the `style.md` cel look against its conformance capsule, the 1.8 m hero, and the hex, and an inspector with details, notes, and Approve / Reject. The inspector takes 36% of the window, for large monitors. The activity log shows every MCP call, and the status bar shows background jobs with progress.
- **MCP:** the binary serves MCP on `http://127.0.0.1:7878/mcp`. `approval_wait` lets the agent block until the human approves or rejects something; `view_screenshot` and `ui_screenshot` let it see what the human sees.
- **Build and WebAssembly:** each system builds as a WebAssembly module and a native static library. Systems run in Wasmtime, one sandboxed instance per run, and the host checks the native build gives byte-identical output (`foundry::det` math, `-ffp-contract=off`). The infrastructure stays, though no systems or channels exist right now.
- **Workspace:** project data lives in `demo/` (`foundry.json`, `conformance/`, `meshy/`, `fixed/`); `--workspace` picks another root. Every name uses `_` as a path separator in the tree. Conformance shapes: `hero`, `prop_medium` (1.48 m tall, 80% of the hero, with a 0.56 m radius), `prop_small`, and `prop_tiny`.
- **Mesh items:** Meshy's model is imported at full fidelity, sized by recorded operations (fit, ground, center, scale, rotate, translate, height) with a hull estimator, reduced to a volume-preserving progressive mesh, and given three LODs by image error (silhouette plus color, 14 views off screen). Each LOD is reordered for the vertex cache (meshoptimizer) and benchmarked on the GPU.
- **LOD limits:** defaults 1% / 5% / 20% are seeds; each item's own limits are what the human tunes. The sliders keep the limits stacked in order (moving one pushes the others), and regenerating rebakes and re-benchmarks only the LODs that changed. Changes to one item take turns, so overlapping regenerations no longer overwrite each other.
- **Switch distances:** each LOD's error is profiled by distance with the game camera (0.9 rad field of view, 1080 lines), with antialiased comparisons. A LOD's switch distance is the first distance at which fewer than the item's switch threshold (default 10%, up to 50%) of its pixels visibly disagree with the full mesh, refined by bisection. View shows a LOD and Zoom shows it from its switch distance (LOD0's Zoom goes to where it matches the full mesh). The stamped manifest records the distances for a game quality factor to scale (`design/submit.md`).
- **Performance graph:** log-scale FPS against instances, starting where the first LOD drops to 1,000 FPS, with the 60 FPS floor and each LOD's budget marked.
- **Stamping:** approving a mesh item stamps its LODs into `fixed/<name>/` with a final manifest and thumbnail. Viewing a fixed asset shows each stamped LOD.
- **Strips:** measured and dropped. On the gnome they were 53% degenerate triangles (Meshy's seams cut them into 3335 strips of 2.2 triangles, and SDL has no primitive restart), so they drew half as many instances as optimized lists.
- **Camera:** orbit, front, side, top, and iso views; Rotate -90 / +90; and a game-camera distance mode used by Zoom (mouse wheel adjusts it, Fit leaves it).
